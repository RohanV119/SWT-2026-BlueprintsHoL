# RBAC Hardening

> Generated: 2026-08-10 14:40:25
> Blueprint: rbac-hardening

---

This repeatable workflow guides you through auditing, hardening, and monitoring role-based access controls (RBAC) in your Snowflake account. It complements the initial role hierarchy created by Data Product Setup by filling operational gaps: assigning users to functional roles, restricting over-privileged system roles, revoking stale access, and establishing ongoing monitoring.

**What You Will Do:**
- **Audit**: Visualize your role hierarchy, discover PUBLIC exposure, find over-privileged users, and detect stale access
- **Harden**: Revoke unnecessary PUBLIC grants, restrict ACCOUNTADMIN to break-glass only, eliminate direct user privileges, and enforce managed access schemas
- **Provision**: Assign end users to functional roles and configure least-privilege service accounts
- **Monitor**: Create governance views, privilege-change alerts, and compliance review documentation

**Key Features:**
- Works with existing Data Product Setup role hierarchies
- Generates review-before-execute SQL (safe dry-run pattern)
- Supports both full-account and per-data-product scope
- SCIM-aware for environments using identity provider integration

Run this workflow periodically to maintain RBAC hygiene as your account evolves.

## Step 1.1: Audit Role Hierarchy

# Role Hierarchy Audit

## Audit Configuration

| Parameter | Value |
|-----------|-------|
| **Audit Scope** | Full Account |
| **Required Role** | ACCOUNTADMIN |

## Queries Generated

| # | Query | Purpose |
|---|-------|---------|
| 1 | Complete Role Hierarchy | Recursive tree of all role-to-role grants |
| 2 | Orphaned Roles | Roles not granted to any parent (unreachable) |
| 3 | Excessive Depth | Roles with hierarchy depth > 5 levels |
| 4 | Role Grant Summary | Aggregate health statistics |
| 5 | Ownership Concentration | Roles owning >10 objects (single point of failure risk) |
| 6 | Ownership Without Parent | Roles that own objects but have no parent in the hierarchy |

## Full Account Scope

All roles in the account are included in the audit. This provides the most complete picture but may produce a large number of results on accounts with many data products.

## What to Look For

### Orphaned Roles
Roles with no parent grant are unreachable from the standard hierarchy. Common causes:
- Data Product Setup was interrupted before wiring the hierarchy
- Roles created manually outside of the blueprint process
- Roles left over from deleted data products

### Excessive Depth
Hierarchies deeper than 5 levels make it difficult to reason about effective privileges. The standard Data Product Setup hierarchy is 4 levels deep: READ → WRITE → CREATE → ADMIN → SYSADMIN.

### Ownership Concentration
Roles owning more than 10 objects are a single point of failure. If the role is accidentally dropped or misconfigured, all owned objects become inaccessible. Consider distributing ownership across schema-level or database-level roles to reduce blast radius.

### Ownership Without Hierarchy Parent
These roles own objects but sit outside the standard hierarchy — they have no parent role and are not reachable from SYSADMIN. This is a structural gap: ownership exists without accountability or a clear governance path. Common causes:
- Roles created manually for one-off migrations or projects
- Leftover roles from decommissioned data products
- Service account roles granted object ownership directly

Remediation: wire each role into the hierarchy (grant it to an appropriate parent), or transfer OWNERSHIP to a correctly-placed role and drop it.

## Next Steps

After reviewing findings:
- Wire orphaned roles into the hierarchy or drop them (Task 2)
- Proceed to **Step 1.2: Audit Privilege Grants** for grant-level analysis

## Step 1.2: Audit Privilege Grants

# Privilege Grant Audit

## Audit Configuration

| Parameter | Value |
|-----------|-------|
| **Audit Scope** | Full Account |
| **Required Role** | ACCOUNTADMIN |

## Queries Generated

| # | Query | Purpose | Severity |
|---|-------|---------|----------|
| 1 | Direct User Grants | Privileges granted to users instead of roles | High |
| 2 | PUBLIC Role Grants | Privileges inherited by all users | High |
| 3 | ACCOUNTADMIN Holders | Users with the most powerful role | Critical |
| 4 | Powerful Privileges | Non-system roles with account-level privileges | Medium |
| 5 | Summary Statistics | Aggregate grant health metrics | Info |
| 6 | Recent Grant Velocity | High-churn grant activity in last 30 days | Medium |
| 7 | Warehouse Size Check | Non-admin roles with USAGE on large warehouses; verify resource monitor coverage | Info |

## Risk Assessment Guide

### Direct User Grants (High)
Any result indicates privileges that bypass your role hierarchy. Each direct grant must be migrated to a role in Task 2 (Revoke Direct User Privileges).

### PUBLIC Role Grants (High)
Each grant is effectively given to every user. Review each and either:
- Confirm it is intentional and add to exceptions list
- Mark for revocation in Task 2 (Restrict PUBLIC Role)

### ACCOUNTADMIN Holders (Critical)
Best practice is 2-3 break-glass users maximum. Compare results against `rbac_accountadmin_users` list in Task 2 (Enforce Admin Separation).

### Recent Grant Velocity (Medium)
Spikes in daily grant activity indicate bulk access events or ad-hoc provisioning outside normal governance. Look for:
- Days with significantly higher grant counts than the baseline
- Grants clustered around weekends or off-hours
- A high number of distinct grantees on a single day

Investigate the specific grants from high-churn days to confirm they were intentional and authorized.

## Next Steps

After reviewing findings:
- Document exceptions for PUBLIC grants
- Compile authorized ACCOUNTADMIN user list
- Proceed to **Step 1.3: Audit Stale Access** before starting remediation

## Step 1.3: Audit Stale Access

# Stale Access Audit

## Audit Configuration

| Parameter | Value |
|-----------|-------|
| **Audit Scope** | Full Account |
| **Required Role** | ACCOUNTADMIN |

## Queries Generated

| # | Query | Purpose | Risk Level |
|---|-------|---------|------------|
| 1 | Dormant Users | Users inactive >90 days with active grants | High |
| 2 | Never Logged In | Users with grants who have never authenticated | High |
| 3 | Unused Roles | Roles with no user assignments | Medium |
| 4 | Health Summary | User activity buckets (Active/Stale/Dormant/Never) | Info |
| 5 | Role Accumulation | Users with >10 active roles (over-provisioned) | Medium |
| 6 | MFA Enrollment Gaps | Active human users with no MFA enrolled (BCR 2025_06) | High |

## Activity Thresholds

| Status | Days Since Login | Action |
|--------|-----------------|--------|
| **Active** | < 30 | No action needed |
| **Stale** | 30 - 90 | Review access, confirm still needed |
| **Dormant** | > 90 | Revoke grants, disable user |
| **Never** | No login record | Investigate — pending onboarding or orphaned |

## Remediation Guide

### For Dormant Users
1. Revoke all role grants: `REVOKE ROLE <role> FROM USER <user>;`
2. Disable the user: `ALTER USER <user> SET DISABLED = TRUE;`
3. After 30-90 day retention period, drop: `DROP USER <user>;`

### For Unused Roles
1. Verify the role is not part of an active hierarchy (check Step 1.1 results)
2. Confirm no automated processes depend on the role
3. Drop the role: `DROP ROLE <role>;`

### For Over-Provisioned Users (>10 Roles)
Role accumulation happens gradually — project access, team changes, and one-off grants that never get revoked. For each user in the results:
1. Review the full role list and identify roles that are no longer needed
2. Revoke excess roles: `REVOKE ROLE <role> FROM USER <user>;`
3. For users with functional roles from multiple data products, confirm each product access is still required

## Next Steps

After reviewing stale access findings:
- Compile the list of users and roles to remediate
- Proceed to **Task 2: Privilege Hardening** for remediation steps

## Step 2.3: Revoke Direct User Privileges

# Revoke Direct User Privileges

## Approach

Direct user-level grants are migrated to role-based access. This ensures all access flows through the RBAC hierarchy defined in Data Product Setup.

## Discovery Queries

The following queries are generated to identify direct user grants:

| # | Query | Purpose |
|---|-------|---------|
| 1 | Direct Object Grants | Privileges (SELECT, INSERT, etc.) granted to users on objects |
| 2 | Migration Template | REVOKE + GRANT pattern for each finding |
| 3 | Summary | Count of direct grants by user and object type |

## Migration Process

For each direct user grant found:

1. **Identify the target role** — Which functional role (READ, WRITE, CREATE) should provide this access?
2. **Verify role coverage** — Does the role already have the required privilege?
3. **Revoke direct grant** — Remove the user-level privilege
4. **Grant role to user** — If the user doesn't already have the functional role

## Verification

After migration, confirm:
- No direct user grants remain (re-run discovery query)
- Users can still access required objects via their roles
- Audit logs show role-based access patterns

## Next Steps

After revoking direct user privileges:
- Proceed to **Step 2.4: Enforce Managed Access Schemas**

## Configuration

| Parameter | Value |
|-----------|-------|
| **Enforce Managed Access** | Yes |
| **Required Role** | SECURITYADMIN or schema owner |
| **Scope** | Full Account |

## Actions

| # | Action | Details |
|---|--------|---------|
| 1 | Discover | Identify all schemas without Managed Access |
| 2 | Enable | Generate `ALTER SCHEMA ... ENABLE MANAGED ACCESS` for each |
| 3 | Verify | Confirm all target schemas have Managed Access enabled |

## Impact

After enabling Managed Access:
- Object owners in these schemas **cannot** grant privileges on their objects
- Only the schema owner and SECURITYADMIN can manage grants
- Existing grants remain in effect (no immediate revocation)
- Future privilege management is centralized

## Verification

Run the discovery query after applying changes. Expected result: **zero schemas without Managed Access** in your target scope.

## Authentication

Each service account uses **key-pair authentication** (RSA). You will need to:

1. Generate an RSA key pair for each service account
2. Set the public key on the user object
3. Store the private key in your secrets manager

```bash
# Generate key pair per service account
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub
```

## Step 4.1: Create RBAC Monitoring Views

# RBAC Monitoring Views

## Configuration

| Parameter | Value |
|-----------|-------|
| **Monitoring Warehouse** | `INFRA_WH_ADMIN` |
| **Scope** | Full Account |

## Views Created

All views are created in `RBAC_MONITORING.VIEWS`:

| # | View | Purpose |
|---|------|---------|
| 1 | `V_ROLE_MEMBERSHIP` | Current role assignments for all users |
| 2 | `V_PRIVILEGE_CHANGES` | Grant and revoke history over time |
| 3 | `V_DIRECT_USER_GRANTS` | Direct user grants (RBAC bypasses — should be empty) |
| 4 | `V_ROLE_HIERARCHY_DEPTH` | Role chain depth with health status |
| 5 | `V_USER_ACTIVITY` | User login activity and dormancy detection |

## Health Checks

After creating the views, verify these health indicators:

| View | Healthy State |
|------|--------------|
| V_DIRECT_USER_GRANTS | **Zero rows** |
| V_ROLE_HIERARCHY_DEPTH | All roles at **HEALTHY** (depth ≤ 4) |
| V_USER_ACTIVITY | No **DORMANT** users with active roles |

## Access

- Views are readable by SECURITYADMIN
- Monitoring queries use warehouse `INFRA_WH_ADMIN`

## Step 4.2: Configure Privilege Change Alerts

# Configure Privilege Change Alerts

## Configuration

| Parameter | Value |
|-----------|-------|
| **Enable Alerts** | Yes |
| **Notification Integration** | `EMAIL_SECURITY_ALERTS` |
| **Monitoring Warehouse** | `INFRA_WH_ADMIN` |

## Alerts

| # | Alert | Frequency | Severity | Trigger |
|---|-------|-----------|----------|---------|
| 1 | `ALERT_NEW_ACCOUNTADMIN_GRANT` | Hourly | Critical | New ACCOUNTADMIN grant detected |
| 2 | `ALERT_DIRECT_USER_GRANT` | Every 6 hours | High | Privilege granted to user (not role) |
| 3 | `ALERT_PUBLIC_ROLE_GRANT` | Every 6 hours | High | New grant to PUBLIC role |
| 4 | `ALERT_DORMANT_USERS` | Weekly (Monday 8 AM) | Medium | Users inactive 90+ days with roles |

## Notification Flow

1. Alert condition checked on schedule
2. If condition is true → notification sent via `EMAIL_SECURITY_ALERTS`
3. Security team reviews and takes action
4. Resolution documented in access review

## Monitoring

View alert history:
```sql
SELECT * FROM TABLE(INFORMATION_SCHEMA.ALERT_HISTORY(
  SCHEDULED_TIME_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP())
)) ORDER BY SCHEDULED_TIME DESC;
```

## Step 4.3: Generate Access Review Report

# Generate Access Review Report

## Configuration

| Parameter | Value |
|-----------|-------|
| **Review Frequency** | Quarterly |
| **Monitoring Warehouse** | `INFRA_WH_ADMIN` |
| **Scope** | Full Account |

## Report Sections

| # | Section | Health Check |
|---|---------|-------------|
| 1 | Executive Summary | User counts, bypass totals |
| 2 | ACCOUNTADMIN Holders | Match against authorized list |
| 3 | RBAC Bypasses | Direct user grants (expect: **0**) |
| 4 | Role Hierarchy Health | Depth violations (expect: all HEALTHY) |
| 5 | Dormant Users | Inactive 90+ days with roles |
| 6 | Recent Privilege Changes | Last quarterly period |
| 7 | PUBLIC Role Grants | Should be minimal |
| 8 | MFA Status | Privileged users without MFA |

## Review Cadence
Run this report **every quarter**. Review lookback period: **90 days**.

## Action Items Template

After each review, complete these actions:

- [ ] Verify ACCOUNTADMIN holders match authorized list (Section 2)
- [ ] Remediate any RBAC bypasses found (Section 3)
- [ ] Fix role hierarchy depth issues (Section 4)
- [ ] Disable or remove dormant user access (Section 5)
- [ ] Review and approve recent privilege changes (Section 6)
- [ ] Revoke unauthorized PUBLIC grants (Section 7)
- [ ] Enable MFA for flagged users (Section 8)
